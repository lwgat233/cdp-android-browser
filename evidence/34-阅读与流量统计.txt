一、用户要什么（原话拆条，逐条对应实现与判据）
────────────────────────────────────────────────────────────────────
① "对主页的话阅读时间就不管，其他网页的阅读时间要记录下来"
   → 采集端按站点记录停留区间；**我们自己的页面（主页 / 控制台 / 播放器 / 测试页）不记**。
     判据：read.add 报一条 appassets.androidplatform.net 的页面 → 记录条数不变；byHost 里只有 example.com。

② "对每个网页的阅读时长记录下来…我要看到饼状图…还要看到柱状图"
   → 饼图 = 按站点占比（带时长与百分比）；柱状图 = 按时间的时长分布。

③ "柱状图是按时间来…按小时来分割，一个小时你看你做了多少"，
   "柱状图上面可能要标记一下多长时间以及多少个网站"
   → 柱子的每个桶都带 ms / visits / **sites（多少个网站）**；桶数 ≤14 时柱子上标"时长·网站数"；
     24 档小时时横轴隔档标刻度；每根柱悬停可看明细（SVG 原生 title，不另写浮层）。

④ "两个计算，一个是计算单独网页，一个是计算使用…连续使用多长时间"
   → usage = {sessions 段数, longestMs 最长一段, continuousMs 当前这段有多长}
     口径：相邻区间间隔 ≤ 5 分钟算同一段连续使用。

⑤ "分别从按天、按月、按年的角度来分析"
   → 粒度四选：小时（固定 24 档，跨天汇总）/ 天 / 月 / 年，标签分别是 20 / 2026-09-20 / 2026-09 / 2026。
     区间跨桶会**按分钟切开**分摊（时间不会记到错的桶里）。

⑥ "第2个功能…流量网络流量…0~24小时内每个小时上行和下行的流量…饼状图分析每个网页使用的流量"
   → 字节**事件**（每次搬运记一条，带 from/to/主机/来源页）→ 小时柱（value=下行, value2=上行）
     + 按站点饼图。字节来源如实标注：应用内下载 / m3u8 分片 / 本地中继转发；
     页面内流量 WebView 不给（拿不到就不编，界面上写明）。

⑦ "它是两个功能，但实质上其实就是收集数据，然后交由一个东西进行统计。绘画。"
   → 结构就是这样落地的：
     采集：ReadLog（阅读区间）/ NetLog（字节事件）——各自只存数据，不做统计。
     统计：**Stats.kt 唯一一处**（分桶 / 会话 / 饼图切片）。
     绘图：**assets/ui/modules/chart.js 唯一一处**（柱状图 + 饼图，纯 SVG，不引第三方库、不联网）。
     界面：**一块「统计」板块**（数据源选阅读/流量 + 粒度四选），两个数据源共用同一套图。

⑧ "数据采集的话还需要分前台和后台…柱状图应该是两色的，下面的可能就是前台上面的这个后台"
   → Fg.kt 记录应用前/后台时间段（Activity 生命周期驱动）；
     阅读记录在**写入当时**就切成 msFg / msBg；字节事件同样切 downFg/downBg/upFg/upBg。
     柱状图双色**堆叠**：下面 = 前台（阅读）/ 下行（流量），上面 = 后台 / 上行，带图例。

二、改了哪些文件

  MainActivity.kt 注册 FgWatcher；中继字节→NetLog；m3u8/普通下载的字节按"来源页"归集；
               下载记录加 page 字段（从 lastPageUrl 取）

  HttpControl.kt /api/read/stats?range=、/api/net/stats?range=

  assets/ui/index.html        「按域名占比」那张卡 → 共用的「统计」卡（数据源 + 粒度 + 刷新 + 清空）
  assets/ui/app.js            loadStats()（唯一渲染函数）、fmtBytes、ch-src/ch-range/ch-go 绑定；

  assets/ui/registry.js       旧行 plugin.readPie → stats.read / stats.net 两行（同一板块，两个功能点）
  assets/ui/style.css         统计图样式（.chart / .chart-legend / .pie-wrap / .chart-empty 等）

三、验收（tools/verify_stats.py，判据全是读回来的事实）
────────────────────────────────────────────────────────────────────
环境自检 → 采集口径（外来页记 / 主页不记）→ 前台后台分开采 → 四种粒度 → 两种口径（站点饼 / 连续使用）
→ 流量（字节事件·分桶·饼）→ 界面（同一块统计画两种图）

  结果：36/36 通过（完整输出见`evidence/34b-统计验收原始输出.txt`）

关键读回值（手工复核过的）：
  read.stats?range=hour     → bars 固定 24 档；桶带 value(前台)/value2(后台)/visits/sites；
                              total 155000ms = totalFg + totalBg（前台+后台）
  read.stats?range=day/month/year → 标签 2026-09-20 / 2026-09 / 2026
  前台/后台探针（手工）：前台报 5 秒 → msFg 5000/msBg 0；
                              退后台再报 5 秒 → msFg 906 / msBg 4094
                              （差的 0.9 秒是按 HOME 到系统真正 pause 的传播延迟，本来就该算前台）
  net.stats?range=hour      → 下载离线测试源后 bytesDown>0、events≥1、bars 有下行、slices 按站点出值
  界面                      → #ch-bar 有柱子、#ch-pie 有扇形、图例「前台/后台」→ 切数据源变「下行/上行」、
                              切「按天」横轴变日期、网络栏目的「统计图」能跳到统计所在栏目

本次抓出来的真缺陷（已修）：
  · app.js 里饼图切片还用旧字段名（h.host / h.ms），而统计器统一出的是 name/value
    → 现象：**饼图空白**（不是报错，静默"还没有记录"）。是"读回 DOM 元素数"的判据抓出来的（path=0）。

测试脚本自己踩的坑（记下来免得下次再犯）：
  · 拿"合成的一条 60 秒记录"去验前台/后台 → 区间落在应用启动之前，大部分本来就该算后台；
    改成"只报刚过去的一小段"，并保证区间完全落在已知的前台/后台里。
  · 按 HOME 到系统真正 pause 有 1~2 秒延迟 → 后台断言不能用"后台独占整段"，要用"后台明显多于前台"。
  · 同一个小时桶里若先有前台记录，会污染"后台 > 前台"的比较 → 先 clear 再测。

四、边界（如实写，不当 bug）
────────────────────────────────────────────────────────────────────
· 页面内的流量字节 WebView **不暴露**给应用：界面里那份"网络流量"统计的是应用自己搬运的字节
  （应用内下载 / m3u8 分片 / 本地中继转发过多少）。开着本地中继时这份数据才接近"整机浏览流量"。
· 停留时间是页面自己报的，切后台/熄屏的时间页面也会算进去 → 它是"停留"不是"专注"（界面里写明）。
· 前后台只按 Activity 生命周期和屏幕状态算；息屏期间应用若被系统冻结，没人来记时间 →
  后台时长只会偏少，不会凭空多出来（宁可少算，不编数据）。
· 阅读记录目前是"一条 = 一次停留（区间）"，长时间挂着会在同一地址上合并；上限 500 条列表展示。
