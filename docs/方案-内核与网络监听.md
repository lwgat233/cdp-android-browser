## 0. 先回答"能不能"

| 想做的事 | 能不能 | 靠什么 | 代价量级 |
|---|---|---|---|
| 看 cookie 的 HttpOnly / Secure / Path / 过期 / 创建时间 | **已经能做** | 读 WebView 自己的 `app_webview/…/Cookies` 库（只读复制一份再查），不需要 root、不需要 CDP | 已实现 |
| 看 HttpOnly cookie 的**值** | 待实测（唯一硬未知点，见 §4.1） | CookieManager（现在）或 CDP `Network.getAllCookies`（备选） | 小 |
| 每个请求/响应的 **header 逐字段** | 能 | CDP `Network.*` 事件（WebView 自带 Chromium devtools） | 中 |
| 响应体（含**二进制**，base64） | 能，但**只给缓存得下的体** | CDP `Network.getResponseBody` | 中 |
| 上行报文体 | 能 | CDP `Network.getRequestPostData` | 小 |
| 请求级拦截且可改可伪造（"不渲染"而不是掐断） | 能 | CDP `Fetch` 域（`continueRequest` / `fulfillRequest` / `failRequest`） | 中 |
| **所有**网络的**全部**二进制字节 | 能，但**只有本机 MITM 代理这一条路**能保证全量 | App 内本地代理 + 自签 CA（只让自己 App 信任，不需要 root） | 高 |
| 换真 Chrome 内核 / CEF | **不做** | — | 见 §5 |

一句话：**"换内核"解决不了问题（安卓 WebView 的内核就是 Chromium，同一份网络栈）；真正的分档在于"用 CDP 从控制面拿数据"还是"在内核下面套一层 MITM 拿全部字节"。**

## 1. 为什么"换 Chrome 内核"是伪命题

- 安卓 WebView 的渲染/网络栈就是 Chromium，和桌面 Chrome 同源；`targetSdk 34` 上跑的是系统那版 Chromium。
- 差距**不在内核**，在**控制面**：Chrome 桌面能装扩展（`webRequest` / `declarativeNetRequest`），WebView 没有扩展机制。
- 而"扩展级控制面"在 WebView 上的等价物**恰好就是 CDP**（WebView 自带 Chromium devtools，debug 版本已开：`tools/verify_cdp.sh` 在用）。
- 安卓上真上 CEF：没有官方/可用发行版，等于自己编 Chromium（数百 GB、小时级构建），收益≈0。
- 控制**外部 Chrome**（App 之外那个）：只能靠电脑 `adb forward` 或 root，且改不了它的 UI、装不了我们的界面 → 与本项目的形态（一个自带控制台的 App）冲突。

结论：**不换内核**。要做的是"把内核自带的 CDP 用起来"+"在下面加一层可选的 MITM"。

## 2. 三档能力对照（现状 / CDP / MITM）

### 档 0 ── 现状（Android WebView API，已实现部分）

| 能力 | 现状 | 硬限制 |
|---|---|---|
| cookie 属性 | ✅ `CookieDb.kt`：复制 `app_webview/*/Cookies` → 读 `is_httponly / is_secure / path / creation_utc / last_access_utc / expires_utc` | 库里 **value 是加密的**（密钥在系统 Keystore），值只能另找来源；只看得到 WebView 见过的 cookie |
| cookie 值 | ✅ `CookieManager.getCookie()` | 只给 `name=value`，属性一概没有；**HttpOnly 的项会返回**（2026-09-22 实测，§4.1） |
| 请求拦截 | ✅ `shouldInterceptRequest` + `AdBlock.kt`（域名后缀 + 关键字 + 隐藏规则 cosmetic，mode=block/hide/both） | 只能拦 WebView 发起的请求；**改不了 WebView 发出的请求头**，要改就得自己在 Java 层重发；规则是自研匹配，不是 ABP/uBO 语法 |
| 代理 | ✅ `ProxyRelay.kt` 本地中继（HTTP/HTTPS/SOCKS5 + 认证 + 白名单直连），字节回调接 `NetLog`；`ProxyController` 设到 `127.0.0.1` | 只**转发**，不看明文（HTTPS 是隧道）；QUIC 不经过 HTTP 代理 |
| 流量统计 | ✅ `NetLog.addProxyBytes`（真实转发字节，非估算） | 只有字节数与主机名，没有逐请求明细 |
| 证书/通路探测 | ✅ `NetTools.kt`（`/api/net/tool` action=ip/resolve/**cert**/tcp/speed） | 只是探测，不参与拦截 |

### 档 1 ── CDP（WebView 自带的 Chromium devtools 协议）

前提：`WebView.setWebContentsDebuggingEnabled(true)`（debug 构件已具备）。**能否在 App 内直连自己的 devtools abstract socket，是本方案的关键未知点（§4.2）**；现在一律靠电脑 `adb forward`。

能得到（对应需求）：

| CDP 域/方法 | 给什么 | 对应需求 |
|---|---|---|
| `Network.getAllCookies` / `Storage.getCookies` | **所有** cookie 的 value + `httpOnly / secure / sameSite / expires / size / domain / path` | log.md 第 1 条（含 HttpOnly 值） |
| `Network.enable` 事件流（`requestWillBeSent` / `responseReceived` / `loadingFinished`） | 逐请求：URL、method、**请求头逐字段**、`postData`、状态码、**响应头逐字段**、mimeType、优先级、timing | 第 9 条（报文逐字段、可筛选、通路） |
| `Network.getResponseBody` | 响应体；**二进制以 base64 回来**（`base64Encoded=true`） | 第 9 条（二进制预览） |
| `Network.getRequestPostData` | 上行报文体（表单/JSON） | 第 9 条（上行） |
| `Fetch.enable` + `continueRequest / fulfillRequest / failRequest` | **拦截并改写** URL/请求头/请求体，或直接伪造响应 | 第 3 条（伪造空响应、不渲染而非硬断）、第 16 条（屏蔽某类资源） |
| `Network.setBlockedURLs` | 一条 URL 模式直接掐断 | 第 3 条的"硬阻断"档（会被站点 JS 探测到，所以不是首选） |
| `Runtime.evaluate` / `Page.*` / `DOM.*` | 已有能力再补一层（页面脚本注入、截图） | 现状已有 |

**档 1 的硬限制（必须写进界面文案，不许假装有）**：
1. **body 只给"内存里还留着的那份"**：大文件、流式媒体分片（HLS/fMP4 那种边下边播）、已被淘汰的体 → `getResponseBody` 报 `No resource with given identifier`。头部/cookie/状态码是**全的**，体不是。
2. 只覆盖**我们 WebView 的**流量；App 内其他网络组件（aria2、ffmpeg、自定义 HTTP）不走它 → 那些要另找来源（aria2/ffmpeg 走的就是档 0/档 2 的路径）。
3. `Fetch` 拦截是**同步阻塞式**：每个请求都要等我们的回包，回慢了整页变慢 → 只对命中规则的请求启用（黑名单/白名单双向过滤）。

### 档 2 ── 本机 MITM（"所有网络二进制都能监听"的唯一保证）

形态：**不是给 Chrome 套壳，而是在内核下面套一层自己的代理**。`ProxyRelay` 已经是骨架，加两件事即可成 MITM：
① 对 `CONNECT` 做 TLS 拆包（自签 CA 现场签发站点证书）；② 把明文请求/响应写进统一的网络记录（并可按规则改写）。

- 明文范围：HTTP 全明文；HTTPS 通过拆包得到完整明文 header + body（含二进制）。
- CA 信任边界：**只让自己 App 信任**（`network-security-config` 的 `trust-anchors` 指向打包进 `res/raw` 的 CA）→ **不需要 root、不影响系统和其他 App**。这是它相比"改系统 CA / 全局 TUN"的关键优势。
- 能得到：逐字段 header、完整体、分块、H2 帧；且**可改、可重放**（这才是"嵌套一层"的完整形态）。
- 代价与坑（逐条要有对策，不然就是埋雷）：
  1. **QUIC/HTTP3 走 UDP**，HTTP 代理抓不到 → 要么禁用 QUIC，要么回退 TCP（需实测回退是否彻底）。
  2. **证书固定（pinning）站点**拆包必失败 → 必须有"拆包失败即直连"的白名单回退，且界面上要看得见"这一路没抓到"。
  3. **性能**：TLS 解密 + 重签 + 内存拷贝，手机上 CPU 明显，大文件传输会变慢。
  4. **存储会爆**：全量存 body 不可行 → 分级存（头部全存 + 体只存前 N KB + 整包按需）。
  5. **敏感数据**：密码/token/身份证类会落进日志 → 默认脱敏，导出与归档时按项目隐私约定处理（密钥/口令不入档）。
- 可复用的现有件：`ProxyRelay`（中继骨架、字节回调）、`NetLog`（时间线存储）、`AdBlock`（同一份规则库做改写）、`NetTools`（证书/通路/测速已有）。

## 3. 判据：每一档怎么"读回来"（不接受"看起来对"）

**档 0（现状基线，回归用）**
- `/api/cookies` 返回项里的 `httpOnly/secure/path/expires` 与 `CookieDb` 直接查库的 `is_httponly/is_secure/…` 逐条一致（同一份库、两次独立读）。
- 读库期间**不得**锁住主库：断言只读复制路径（`cacheDir/cookiedb/Cookies.copy`）被创建并删除，主库 mtime 不变。

**档 1（CDP）**
1. 打开一个已知站点，抓回来的请求记录里出现该 URL 的**逐字段请求头**，且含 `Cookie:` 行与 `User-Agent`（与页面实际一致）。
2. 同一 URL 取响应体两次：**长度 == `Content-Length`**，且两次 sha256 相同（幂等）。
3. 取一个二进制资源（png 或 mp4 分片）：base64 解码后**前 8 字节**与文件头签名一致（png `89 50 4E 47`，mp4 `ftyp`）。
4. `Fetch` 拦截：注入一条规则命中某 URL 并 `fulfillRequest` 空响应 → **页面 DOM 里该元素不存在**（读 DOM 文本判定，不看截图），且拦截计数 +1。
5. 诚实断言：对**分片媒体**取体，必须**明确返回"拿不到体"**，而不是返回半截或空当成功。

**档 2（MITM）**
1. 抓一个 https 站点：代理侧记录里出现**明文** 请求行（`GET /… HTTP/1.1`）与 `Host/UA/Accept` 字段，且与档 1 的 `requestHeaders` 逐字段一致。
2. **字节对账**：经代理下载一个已知文件，代理侧累计字节 == 落盘文件大小（项目已有同款口径：`198658 == 198658`）。
3. 信任边界：另一个 App（系统浏览器）访问同一站点**仍正常**，且**不经过**我们的代理（代理侧记录里没有它）。
4. 关掉 MITM 后：页面无证书告警，所有请求恢复直连。
5. 回退可见：pinning 站点拆包失败时，记录里必须有"未拆包/直连"这一条，而不是静默没有。

**共同的防假阳性**：不许用"页面能打开"当证据；不许拿 CDP 的字节数当 MITM 的明文证据；每条断言失败要能打印"为什么"。

## 4. 动手前必须实测的未知点（只有两个，代价都很小）

### 4.1 ✅ 已实测（2026-09-22）：HttpOnly 的**值**不用 CDP 也能拿
- 实测：`CookieManager.getCookie()` **返回** HttpOnly cookie 的 `name=value`（`hocookie=ho_val` 在列表里）；
  缺的只是**标记**，标记从 WebView 自己的 cookie 库 `is_httponly` 读（已实现于 `CookieDb.kt`）。
- 但实测发现更关键的坑（真因见 `evidence/47-cookie属性实验（落盘时延与CDP）.txt`、登记 B-82）：
  库里那份**滞后**（批量提交，刚写的 cookie 3 秒读=0 行，60 秒才有；读前先 `flush()` 则 1 秒内全在），
  且**前端把属性字段写死成文案**（`app.js:2443`）→ 用户看到"无效值"。→ 结论：档 1 对 cookie 的增益从"必须"降为"可选（无落盘时延 + 一次给全）"。
### 4.2 App 自己能不能直连 webview 的 devtools socket（决定档 1 的落地形态）
现在一律电脑 `adb forward`（`tools/verify_cdp.sh`）。devtools 是 abstract unix socket（`webview_devtools_remote_<pid>`），同 uid 理论上可连。
- 判据：App 内连上后发 `Browser.getVersion`（或 `Target.getTargets`）拿到合法 JSON 回包，且**无需电脑**。
- 影响：通了 → 档 1 可以纯 App 内自用（用户不需要电脑）；不通 → 档 1 只能"连着电脑时可用"，界面必须如实标注。

## 5. 明确不做什么（写下来，避免以后又被当成需求）

- **不换内核**（CEF/自编 Chromium/外部 Chrome 控制）：收益≈0，代价极高。
- **不承诺"100% 全部字节"**：QUIC、pinning 站点、App 内非 WebView 组件、系统代理绕过（app 自带网络栈的第三方库）都是"抓不到就是抓不到"，如实显示缺口。
- **不做系统级 CA / 全局 TUN 当默认**：只覆盖自己 App；要全局是另一件事（用户已有 mihomo/TUN 那套，但那抓到的是密文）。
- **不把敏感数据默认落盘**：cookie 值、POST 体、token 默认脱敏。
